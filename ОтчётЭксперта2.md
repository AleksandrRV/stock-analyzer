## Итог: по решению об «обрезке» графика — полностью согласен с экспертом

Пересчёт кривой на каждый клик по таймфрейму — это не архитектурная лень, а необходимость, и не только из-за требования «база 0%»:
- **ALL-кривая хранит точки только в milestones/концах месяцев.** Кнопки 1M/3M/1Y/YTD и тем более «свой период» почти никогда не попадают ровно в одну из этих дат — а значит, даже технически нечем «отрезать»: нужной опорной цены на начало отрезка в сохранённом массиве просто нет.
- Раз всё сырьё (цены/дивиденды) уже в IndexedDB и защищено RAM-lock (`withLock`), пересчёт — это чтение из кэша + арифметика, а не поход в сеть. Обновление в `archtecture_and_buisnes.md` (п. 5.4) корректно фиксирует это как осознанное решение, а не забытую оптимизацию. Замечаний нет.

## Осталось не исправлено / новые замечания

**1. Ключ часового кэша не содержит дату — риск «протухшего» кэша на сутки.**
`usePortfolioCalculation.ts` и `MonthlyReturnsMatrix.tsx`: `calculatedAtHour = new Date().getHours()` — это число 0–23 без даты. Если вкладка/установленное PWA-приложение не перезагружается больше суток (обычный сценарий для «оффлайн-первого» приложения), то в тот же час следующего дня кэш будет ошибочно считаться свежим — портфель не пересчитается, хотя должен. Решение: использовать метку часа с датой, например `Math.floor(Date.now() / 3_600_000)` (часовой таймстемп) вместо `getHours()`.

**2. Очистка рыночного кэша в Настройках так и не сбрасывает кэш расчётов.**
`SettingsView.tsx` не менялся вообще (проверил побайтово) — `handleClearCache` по-прежнему не вызывает `clearCalculationCache()`. Раньше это «протухляло» только `calculationsCache`, теперь — ещё и новый `matrixCache`. Все остальные точки мутаций (`addMilestone`, `updateSettings`, `restoreFullData`, `ManualDividendsModal` и т.д.) корректно дёргают `clearCalculationCache()`, а именно это место — нет. После очистки кэша пользователь по-прежнему будет видеть старые цифры, хотя тост обещает обратное.

**3. `clearFundPricesOnly`/`clearStockPricesOnly` — исправлено частично, не по корню.**
Вместо одного хардкода `'LQDT'` теперь список `KNOWN_FUNDS = ['LQDT','SBMM','AKMM','TRUR']`. Это лучше, но проблема та же по сути: тип актива по-прежнему не хранится в таблице цен, а тикер фонда пользователь может ввести любой (форма добавления актива не ограничивает список). Любой фонд вне этих четырёх тикеров снова будет неправильно чиститься («акции» его удалят, «фонды» — не удалят). Полноценное решение — хранить тип актива вместе с ценой (или отдельным реестром тикер→тип), а не расширять список исключений.

**4. Мелкое, не исправлено:** в `PortfolioDetailView.tsx` подсказка о переименовании тикера у актива точки (`TickerResolver.resolveTicker(asset.ticker, milestone.date)`) по-прежнему вызывается без `customRenames` из настроек — косметика, на сам расчёт не влияет.

**5. Главный оставшийся резерв скорости — распараллеливание уже сделано только «вглубь», но не «вширь».**
Внутри одного суб-периода активы теперь считаются параллельно — отлично. Но внешние циклы всё ещё последовательны:
- `calculatePortfolio`: `for` по контрольным точкам, `await this._calculateSubPeriodReturns` на каждой (строка ~352);
- `calculateMonthlyReturnsMatrix`: `for` по годам/месяцам, тот же `await` на каждой ячейке (строка ~476);
- `calculateChartCurveForRange`: `for` по точкам таймлайна (строка ~307).

Для первых двух это чистая последовательность без необходимости: каждая точка/месяц считается независимо от других, синхронизация нужна только на этапе агрегации (`calculateCompoundReturn`). Их можно и нужно запускать через `Promise.all` по всем точкам/месяцам сразу, а не по одной с `await` в цикле — это тот же приём, что уже применили на уровне активов, просто ещё не поднятый на уровень выше.

Для графика (`calculateChartCurveForRange`) полная параллелизация впрямую невозможна — там реально накопительный процент (`cumPortfolioMult *= ...`), который обязан считаться по порядку. Но можно разделить два этапа: сначала параллельно (`Promise.all`) получить «сырые» проценты доходности каждого суб-периода (то есть сделать всю тяжёлую сетевую/кэш-работу разом), а затем быстрым синхронным проходом свернуть их в накопительную кривую — эта часть уже не требует await и займёт доли миллисекунды. Для матрицы за много лет (годы × 12 месяцев) и для портфелей с десятками точек это даст ощутимо больший эффект, чем распараллеливание только по активам внутри одной точки.

**6. Не затронуто (осталось как было):** `MarketDataSyncService`/`MoexApiGateway` по-прежнему запрашивают цену «по одной дате за раз» на тикер, а не всем диапазоном одним запросом с `bulkPut` в IndexedDB. Для уже прогретого кэша (в пределах часа) это не критично, но на первой загрузке нового/непросмотренного портфеля именно это, а не последовательность await, скорее всего останется главным источником задержки — стоит держать в бэклоге как следующий шаг.
