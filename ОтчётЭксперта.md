# Подозрение на ошибки в коде

1. **Сдвиг даты «конец месяца» на MSK — `PortfolioCalculationService.getMonthEndDatesBetween`**
   Конец месяца строится как `Date.UTC(..., 23, 0, 0)`. При переводе в MSK-дату (+3ч, `toMSKDateString`) 31 января 23:00 UTC превращается в «1 февраля» — то есть точка «конец месяца» на самом деле смещается на следующий день. Это искажает точки на графике и границы «Матрицы доходностей по месяцам». Решение: строить конец месяца часом, который не пересекает суточную границу MSK (например, 20:00 UTC или раньше), либо считать границу сразу в MSK-логике.

2. **Поля `datetime-local` предзаполняются UTC-временем вместо локального — `MilestoneEditorModal.tsx` и `ClosePortfolioModal.tsx`**
   Используется `now.toISOString().slice(0,13)+':00'`, а `toISOString()` отдаёт время в UTC, тогда как `<input type="datetime-local">` ожидает локальное время устройства. Для пользователей в МСК (целевая аудитория) поле по умолчанию показывает время на 3 часа раньше реального. Решение: собирать строку из локальных `getFullYear/getMonth/getDate/getHours()`, а не из `toISOString()`.

3. **Не реализован часовой автопересчёт открытых портфелей — `usePortfolioCalculation.ts` / `usePortfolioStore.ts`**
   По документации доходность точки без «финиша» должна пересчитываться каждый новый час. Фактически `calculationsCache` не хранит время расчёта и никогда не протухает сама по себе — пересчёт происходит только при явных действиях (правка точки, смена настроек, ручной дивиденд, очистка БД). В итоге открытый портфель может показывать устаревшие цифры сколько угодно долго. Решение: хранить вместе с кэшем «час расчёта» и инвалидировать запись, если текущий час отличается.

4. **Очистка рыночного кэша не сбрасывает кэш расчётов — `SettingsView.handleClearCache`**
   После очистки IndexedDB (`marketDb.clear...`) не вызывается `clearCalculationCache()` из стора. Уже посчитанные карточки/детали портфеля продолжают показывать старые цифры, хотя тост обещает, что «котировки скачаются заново». Решение: после любой очистки кэша дополнительно сбрасывать `calculationsCache`.

5. **`clearFundPricesOnly` / `clearStockPricesOnly` работают только с жёстко зашитым тикером `LQDT` — `marketDb.ts`**
   Таблица цен не хранит тип актива (STOCK/FUND), поэтому «очистить только фонды» реально чистит только LQDT, а любой другой фонд (например SBMM или пользовательский тикер с типом «Фонд») не удаляется вовсе. А «очистить только акции» наоборот — по ошибке удаляет цены таких фондов, так как они не равны LQDT/MCFTR. Решение: хранить тип актива вместе с ценой (или отдельным реестром тикер→тип) и фильтровать очистку по нему.

6. **`mcftrTotalProfitPercent` всегда возвращается как 0 — `PortfolioCalculationService.calculatePortfolio`**
   Поле явно предназначено для общей доходности индекса за весь период (аналог `totalProfitPercent` портфеля), но в возвращаемом объекте жёстко стоит `0`, хотя рядом уже считается `mcftrStart`/`mcftrFinish`. Похоже на недоделанную реализацию. Решение: посчитать `((mcftrFinish - mcftrStart) / mcftrStart) * 100`, как это уже делается для месячной версии.

7. **Тройное дублирование одного и того же расчётного блока (~40 строк) — `PortfolioCalculationService.ts`**
   Логика получения цен/дивидендов/LQDT/MCFTR для суб-периода почти дословно скопирована в `calculateChartCurveForRange`, `calculatePortfolio` и `calculateMonthlyReturnsMatrix`. Риск: исправление бага/бизнес-правила в одном месте легко забыть внести в остальные два. Решение: вынести общий метод расчёта доходности одного суб-периода и переиспользовать его в трёх местах.

8. **Подсказка о переименовании тикера не учитывает пользовательские правила — `PortfolioDetailView.tsx` (список активов точки)**
   `TickerResolver.resolveTicker(asset.ticker, milestone.date)` вызывается без `customRenames` из настроек — используется только встроенный список. Сам расчёт доходности использует правильный список, страдает только визуальная подсказка «(TCSG → T)» для собственных правил пользователя. Решение: передавать `settings.tickerRenames`.

9. **Импорт бэкапа не валидирует содержимое портфелей — `filePortability.parseImportFile` / `restoreFullData`**
   Проверяется только версия схемы и то, что `portfolios` — массив. Сумма весов активов в точке, обязательные поля и т.п. не проверяются, хотя в UI редактирования такая защита (`isOverallocated`) есть. Повреждённый или вручную изменённый файл может быть восстановлен без предупреждения и привести к некорректным расчётам. Решение: добавить базовую валидацию структуры/данных при импорте.

10. **Непроэкранированный пробел в URL — `MoexApiGateway.fetchClosePrice`**
    В строке запроса `till=${mskDateString} 23:59:59` пробел не закодирован. Формально это невалидный компонент URL и может вести себя непредсказуемо в разных окружениях/полифилах fetch. Решение: закодировать значение параметра (`encodeURIComponent` или заменить пробел на `%20`/`+`).

# Предложения по оптимизации

1. **Последовательные (`await` в цикле) запросы вместо параллельных — все три метода `PortfolioCalculationService`**
   Цены и дивиденды по каждому активу и каждому суб-периоду запрашиваются строго друг за другом, хотя они независимы. Особенно тяжело это бьёт по «Матрице доходностей по месяцам» (суб-периодов = месяцы × активы). Независимые запросы стоит запускать параллельно (`Promise.all`), а ещё лучше — избавиться от самой необходимости стольких обращений (см. п.2).

2. **Точечная загрузка цены «по одной дате» вместо целого диапазона свечей — `MoexApiGateway` / `MarketDataSyncService`**
   Каждая нужная дата по тикеру запрашивается отдельным HTTP-вызовом к ISS MOEX. При первом обращении к новому тикеру логичнее сразу забирать весь диапазон дневных свечей за интересующий период одним запросом и сохранять пачкой (`bulkPut`) в IndexedDB, а все последующие даты этого тикера брать уже из кэша без сети. Это на порядок сократит число сетевых запросов и время первой загрузки портфеля/матрицы.

3. **Нет кэширования матрицы доходностей и «полной» кривой графика — `MonthlyReturnsMatrix.tsx`, `PortfolioChart.tsx`**
   В отличие от `calculatePortfolio` (кэшируется в Zustand), матрица пересчитывается с нуля при каждом монтировании компонента, а переключение таймфреймов графика (1M/3M/6M/1Y/YTD) каждый раз заново дёргает движок расчёта. Стоит кэшировать результат матрицы и «ALL»-кривой в общем сторе аналогично `calculationsCache`, а фильтры графика по времени вычислять на клиенте обрезкой уже готового массива точек, не пересчитывая заново.

4. **Отсутствие TTL по часам у кэша расчётов** — раз бизнес-логика подразумевает обновление раз в час, стоит при заходе на дашборд/детали портфеля сравнивать «час последнего расчёта» с текущим часом и пересчитывать только при расхождении. Тогда в течение часа переходы между разделами и повторные заходы в приложение будут происходить без спиннеров вообще, как и требуется.

5. **`DashboardView` безусловно перечитывает localStorage при каждом монтировании (`loadFromStorage`)** — все мутации стора и так одновременно обновляют и память, и localStorage, поэтому полноценная загрузка нужна только один раз при старте приложения, а не при каждом возврате на дашборд.

6. **Настройки читаются из localStorage и парсятся заново в начале каждого расчёта** (`UserStorage.getSettings()` в трёх методах движка) — при частых пересчётах (переключение таймфреймов, открытие матрицы) можно держать разобранные настройки в памяти и инвалидировать только при их реальном изменении.

7. **Параллелизм между карточками портфелей на дашборде уже есть** (каждая карточка сама вызывает `usePortfolioCalculation`), но общее время всё равно определяется самым «тяжёлым» портфелем из-за последовательности внутри одного расчёта — максимальный эффект даст именно устранение N+1-запросов внутри `PortfolioCalculationService` (п.1–2).
